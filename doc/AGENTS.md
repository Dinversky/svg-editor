# Documentation Maintenance

Please maintain `doc/README.md` as the unified course documentation for this project. Adhere to the existing assignment requirements and ensure all mandatory sections are included.

## 0. Documentation Structure
### Architectural Design

| #   | Item | Requirements |
| --- | --- | --- |
| 1   | **Module Partitioning** | Define the modules (directories) into which the code is organized and the **responsibilities of each module**. Include a diagram (a PlantUML component or package diagram). |
| 2   | **Design Pattern Selection** | Which design patterns have you chosen to implement, and how are they applied within the codebase? (The Command pattern is required.) |
| 3   | **Dependency Rules** | Clearly specify which modules are permitted to depend on others, along with the rationale. Any dependencies that violate these rules must be noted as items to be addressed. |
| 4   | **Anticipated Points of Change** | Identify the areas most likely to undergo future changes. List them individually and explain what provisions you have made for them—or, conversely, **why you decided not to make any such provisions**. |

### Process Documentation

Document key or representative discussions and iterations—for instance, any issues identified in suggestions, documentation, or code generated by an AI, and the steps taken to verify and rectify them.

### Consistency Self-Check

Upon completion of the implementation, review your work against the architectural design and answer the following:

1. **Module Partitioning**: Does the actual directory structure align with the design? If there are discrepancies, have they been noted in the revision log?
2. **Dependency Rules**: Have any of the defined dependency rules been violated? (You may perform a spot check to ensure that the actual code dependencies remain consistent with the architectural design.)

### Quality Assurance

Explain how you verified that the final codebase is functionally complete, and provide the basis for your confidence in the quality of the code.

## 1. Development Process Record

- The development process record must cover the entire project lifecycle—from initial setup, through implementation, testing, and refinement, to final delivery. It should not be limited solely to the most recent tasks or development iterations. - Record progress at key milestones—for example, upon completing a development phase, making a significant architectural decision, resolving a major issue, or finishing a critical validation step.
- Do not create separate entries for individual prompts, minor code tweaks, or repetitive implementation attempts. Instead, consolidate related iterations into the corresponding milestone entry.
- If a milestone is already covered by an existing entry, update that entry rather than creating a duplicate record.
- Maintain a clear history of significant decisions, design changes, issues, solutions, and validation results. Explicitly distinguish between completed work and tasks that are planned or yet to be finished.
- Record only verifiable facts (e.g., data from repository history, task logs, code, test outputs, or other available evidence). Do not fabricate past decisions, implementation details, or test results.

## 2. Living Documentation Sections

- Ensure that documentation regarding architectural design, self-consistency checks, and quality assurance (QA) remains aligned with the current implementation and project requirements.
- When changes occur in code, architecture, testing, or validation practices, update the existing sections directly; do not create a full copy of a section for every iteration.
- Describe the actual current architecture, implemented design patterns, module responsibilities, dependencies, and any known deviations. Never describe "planned features" or "intended design patterns" as "implemented."
- Document only those quality assurance practices that have actually been configured or executed. Clearly distinguish between automated tests, type checks, continuous integration (CI) checks, manual reviews, and any checks that have not yet been performed.
- Retain information regarding unresolved issues and their associated limitations until they are either resolved or explicitly accepted (i.e., acknowledged as not requiring a fix).

## 3. When to Update Documentation

- After reaching a key milestone, evaluate whether a new entry should be added to the development record or if an existing entry requires an update.
- Whenever a change significantly impacts the content described in the "Living Documentation" sections, update the relevant documentation accordingly. - Before completing a task, verify that the documentation content aligns with the current codebase and the actual validation results of the task.
- Avoid redundant descriptions. If additional information is required, update existing sections or milestone entries rather than duplicating the information elsewhere.

## 4. Scope and Accuracy

- Do not implement extra features solely for the sake of making the documentation appear "complete."
- Do not delete or rewrite historical records, as this may obscure significant development decisions or events.
- You must adhere to the documentation structure required by the task. If a requirement conflicts with the current implementation or other instructions within the repository, report the conflict accurately; do not claim that a requirement has been met if it has not actually been fulfilled.
- In your task report, summarize the changes made to the documentation and indicate which parts remain incomplete or require future updates.
